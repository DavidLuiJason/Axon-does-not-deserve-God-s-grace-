## 2. WHAT AXON IS FOR, AND HOW IT MUST FEEL
AXON is an Android app (Capacitor, React, TypeScript; built in Google AI Studio, kept in GitHub, built to an APK by GitHub Actions). It must be an intelligent, truthful, conversational assistant with an English dictionary as its understanding, plus tools and media. It reads what is said and what came before, finds several instructions in one message, answers each, notices mistakes, says plainly what it does not know, and never claims an ability it lacks. Big assistants do this inside one trained model; AXON uses explicit, testable parts and may add a model later as a second tier supervised by those checks. The real work is the language layer; the dictionary is only its first ingredient.
**Design philosophy (owner, 2026-10-16, binding on every screen):** simple, clear, organised, professional. The person must understand a page at a glance: what it does, what they can do, where to go next. No floods of details, long lists or complicated navigation. Show the few main choices first; reveal the rest only when the person goes in (progressive disclosure). A pretty screen that is hard to read is a failed screen. History: an earlier AXON was scrapped because it piled things on top of things until looking at it was painful; the owner saw the same signs again in this one in October. Every screen prompt must say this, and each screen is checked against it. **One look everywhere (decided 2026-10-17):** the same header band on every screen (logo fixed at the left, "AXON" bold with the page name lighter beside it, small-caps line under); the back control is a slim row UNDER the band, never in front of the logo; lists are plain rows (36 px icon, name, chevron), no boxed cards; no per-row "Coming soon" badges (unbuilt items dimmed, one quiet line says so); the Tools home shows group names only. A header may fold away ONLY on editor screens (opt-in, shared ScreenHeader, a later AI Studio job). Source, Build and Interface Capture screens are locked: do not restyle them.
**Look:** keep the current identity (dark, calm, #ECECEC text, lucide icons, small-caps taglines, header band). Do not add colours, fonts or icon sets. Inspiration from other apps is welcome; the result must look like AXON.

## 4. THE BUILDING RULES (the owner's sayings; apply before every plan and stage)

## 7A. THE MIND SYSTEM (owner vision 2026-10-20; full text and the Director's opinions: `docs/AXON_VISION.md`; job order `docs/BRAIN_PLAN.md`)
**The brain is a LOOP plus tools.** Observe, understand (the stages of 7), plan ONE step, act through a tool, check the result, remember, repeat until the task's own success test passes, a step budget ends it, or it must ask. Every capability is a tool controllable by chat (FL10). The thinking is AXON's own stages; outside AI tools (AI Studio and the like) are TOOLS under the Charter, never the brain.
**Four stores and a fence, never mixed:** CHARTER (fixed rules and permissions, signed by the owner; AXON can never edit or widen it); KNOWLEDGE (claims that passed the truth gates); MEMORY (what AXON earned by working: episodes, lessons, corrections, preferences, style profiles, and a JOURNAL of every action, so it is accountable); CONTEXT (what the owner gives for this task). Standing files read before EVERY task: Charter, preferences, mistake ledger, tool notes.
**Never silently wrong** (the honest form of "never makes a mistake"): compute, never recall; an independent second path where cheap; abstain and ask when unsure; every claim carries a label (PROVEN, CONFIRMED, CHECKED, REPORTED, UNSURE); every tool is CERTIFIED by known-answer tests and has a known-bad switch that also lists the past answers it touched; every correction becomes a permanent regression test plus a ledger entry; the owner is told what was handled and what needs a decision.
**Truth gates (knowledge in):** provenance; source tier and credit; independent agreement; date and expiry; contradiction check; executable test where possible; scope check (claim cut to what sources say); adversarial check (strongest counter-evidence, known failures); owner approval when stakes are high. Output is a tier, never a bare fact; only PROVEN and CONFIRMED are stated as fact.
**Council (inside the brain, not many models):** independent deterministic reviewers (Meaning, Math and Evidence, Guardrail and Permission, Reader and Style, Adversary) each return a verdict with a reason; a Chair merges; a hard veto blocks; disagreement is shown to the owner.
**Lanes and tasks:** a LANE is a standing area (Email, Messages, Files, Media, Code, Security, Learning, Money) with its own actions, tools, permissions, memory and playbook; a TASK is one job in a lane. Every action is ALLOWED, ASK (the owner approves first) or NEVER: the owner is the approver, not the operator. Sending, deleting and money start at ASK or NEVER. A scheduler gives priorities, parallel workers and preemption of long jobs.
**Hands:** one tool bus: built-in tools, APIs, MCP servers (network), CLI only on a remote machine; then AXON Web (network) and AXON App (screen reading and app control by Android accessibility and screen capture, permission by permission, in a Permissions screen). Everything outside passes the permission broker and is logged. Private by default; data stays on the phone.
**Growth path:** measure (corpora, mistake ledger), find the weakest area, gather knowledge through the gates or write tests, fix or add, run every test, promote, log, repeat. TURNING POINTS (facts that change a plan's direction or quality) are flagged to the owner.
**Writer:** an audience model (a person reads slowly and tires: short lines, structure; an AI tool needs complete, explicit, tested prompts and its known failure modes from a Tool Knowledge Pack) and a Reading Comfort style; a Dictation Cleaner for voice (punctuation, fillers, self-corrections; the phone's recogniser supplies the words).
**Stated plainly:** no zero-error promise, only no silent error; no self-copying and no autonomous spending (parallel workers under the owner's own accounts, with budgets); security testing only on systems the owner declares; imitating a person's writing only with their consent; drafts are approved before anything is sent.
**Order:** M0 Charter and permission broker; M1 loop skeleton and journal; B3 and B4; M2 memory; M3 truth gates and tool certification; M4 council; M5 objective and writer; M6 lanes and scheduler; M7 hands (Web first, App second); M8 learning, style, dictation; M9 AXON Code harness.

## 12. LESSONS AND FAILURE PREVENTION (full catalogue: `docs/DIRECTOR_HANDBOOK.md`)
Real failures: tests that do not block the build let defects pass (run them); acceptance numbers must be derived, never remembered; a fix from a hypothesis did not cure the failure (measure first; the image view fault is the second round on one area); overloaded builders fail (one big job made ChatGPT build nothing; a reply with only a Law Check is a failed delivery); a zip is not "the project" until you know what the tool that made it leaves out; a third attempt after two failures breaks FL4; starting work without the Law Check breaches FL11; adding phrases is not building intelligence (FL13); a golden transcript recorded from new code proves nothing alone; pure engines can be proven in a sandbox but a screen on a real phone cannot (React layers and touch need the owner's phone test); the Director sandbox type-checks only single files, so every ChatGPT report shows its own `tsc` result and the cloud build is the real proof; ChatGPT cannot judge how a screen looks, AI Studio can.
**Prevention rules:** every prompt is sized to what the builder was proven to carry and says what to deliver if it cannot finish; every prompt names its base files and says STOP if missing; engine jobs only create files; screens never re-implement engines; the Director never merges without `verify_return.py` and a report; the board is updated after every step.

# AXON VISION AND THE DIRECTOR'S OPINIONS (2026-10-20)

Source: the owner's long voice message of 2026-10-20 (kept whole in the chat), restructured. Short form: roadmap section 7A. This file explains WHY, says where the Director disagrees or would build differently, and lists what is decided and what is not. The owner asked for real thinking, restructuring and objections; this is that.

## 1. What the owner described, in one paragraph
A private assistant that works for its owner only, understands what is meant (not just what is typed), plans and does work through tools (its own, apps, the web, outside AI tools), remembers what it did and why, learns from corrections, checks itself so it is never silently wrong, writes in a way people and other AI tools can actually use, never crosses a fence the owner set, and gets better by a repeatable path. Every capability is reachable by chat from anywhere in the app.

## 2. The structure (the answer to "what are we actually building?")
```
CHARTER (fence)  allowed / ask first / never. Owner-signed. AXON cannot edit or widen it.
   |
PERCEIVE  chat text | cleaned dictation | files | later: web pages, screens, apps
   |
UNDERSTAND  Reading > Analysis > Meaning (what is said) > OBJECTIVE (what for, what counts as done, for whom)
   |
THE LOOP   observe > understand > plan ONE step > act through a tool > CHECK > remember > repeat
   |            ^ asks the owner when unsure, when the step is ASK, or when the budget ends
   |            COUNCIL reviews the plan and the result (deterministic reviewers, Chair, veto)
   |
HANDS (tool bus) built-in tools | APIs | MCP servers | remote CLI | AXON Web | AXON App (screen and apps)
   |
WRITER  audience model, Reading Comfort, honest labels
   |
STORES  KNOWLEDGE (gated truth) | MEMORY (episodes, lessons, corrections, style, JOURNAL) | CONTEXT (this task)
```
Standing files read before EVERY task: Charter, preferences, mistake ledger, tool notes (what each tool is, can do, cannot do, its version and last certification).

## 3. Answers to the owner's questions
- **Is an agent a loop?** Yes. One step toward the job, look at what happened, decide the next step, repeat. Four things make it safe and useful: a step budget (it cannot run forever), a success test written BEFORE it starts, an approval gate on risky steps, and a journal entry for every step. Without a language model the "decide the next step" part is AXON's planner choosing among abilities it was given; it is reliable inside what it knows and honest outside it.
- **Context versus memory:** the owner is right. Context is what you give for this task and dies with it. Memory is what AXON earned by working and survives. Add two more that must stay separate: KNOWLEDGE (claims that passed the truth gates; shared across tasks) and CHARTER (rules; not learned, only set by the owner). Mixing these four is how assistants become unreliable.
- **Do we need a "context layer" or just intelligence?** Both, and they are different jobs. Intelligence (the stages) decides; the stores supply facts to decide with. A brain with no stores is amnesia (the owner refuses that); stores with no stages is a filing cabinet.
- **Lanes and tasks:** a TASK is one job ("draft this email"). A LANE is a standing area with its own set of allowed actions, rules and memory ("Email": read, draft, reply, archive, delete, each with a level ALLOWED, ASK or NEVER). Lanes are how one assistant can run Email, Messages, Files, Media, Code, Security and Learning without one lane's permissions leaking into another. It is not only email; any area gets a lane.
- **Council:** the Director could not find an official Anthropic feature called Council. What circulates under that name is the "LLM council" idea (Karpathy's): several independent advisers answer alone, rate each other anonymously, and a chairman combines them. AXON should have the IDEA, built its own way: independent deterministic REVIEWERS (Meaning, Math and Evidence, Guardrail and Permission, Reader and Style, Adversary), a Chair, a hard veto, and disagreement shown to the owner. Reviewers are code with tests, not many models; that is cheaper, faster on a weak phone, and testable. If an outside model is ever connected (see decisions) it can sit as one more reviewer, never as the Chair.
- **"It must never make a mistake":** impossible to promise, and a promise of it would itself be a lie. What AXON CAN promise, and the Director recommends as the written standard: NEVER SILENTLY WRONG. Concretely: (1) compute, never recall; (2) a second independent path where cheap (a different method reaches the same number); (3) abstain and ask when unsure; (4) every claim labelled PROVEN, CONFIRMED, CHECKED, REPORTED or UNSURE; (5) every tool CERTIFIED by known-answer tests before it is trusted and re-run at startup, with a known-bad switch; (6) every correction becomes a permanent regression test plus a ledger line; (7) the journal knows which answers used which tool version, so if a tool is later found wrong AXON can say "these 3 answers are affected" instead of "you were right, sorry". The calculator story the owner feared (it said the answer, was wrong, then admitted the tool was wrong) is prevented by (2), (5) and (7). Real example found today: the calculator returns a syntax error for percent forms; failing loudly is the safe failure, and C19 fixes the cause.
- **Truth filters, how many layers:** nine gates, each cheap and testable (see section 4). Knowledge is accepted per CLAIM, not per source, because good sources print wrong claims.
- **Learning by training:** without a model, "training" means three things AXON can really do: (a) take in knowledge through the gates, (b) turn every correction into a test and a lesson, (c) improve its own measured weak spots by the growth path. It will not learn by adjusting hidden weights, and that is a strength: every lesson is a file the owner can read, edit or undo.
- **Codex:** as far as the Director knows, Codex is a harness around a coding model: a loop, tools to read and search files, edit by patch, run commands and tests in a sandbox, approval levels (read only, auto, full access), and a standing instruction file read at the start. All of that CAN be copied and is exactly what AXON needs. The part that cannot be copied is the model that writes new code. So AXON Code = the full harness plus a pluggable CODER slot. Until a coder is connected AXON must say exactly what it needs ("connect a coder: here are the options"), never "I am incapable". This is the strongest reason to allow outside models as permissioned tools (decision D1).
- **Python or JavaScript?** Different languages. A phone's app screen (WebView) already contains a JavaScript engine, so JS needs no download. Python is not in the phone's WebView; it needs its own interpreter built for the browser (about 10 MB class, slower to start, more memory). So: JS built in, Python as an optional measured pack offered only on phone tiers that can carry it.
- **AXON Web and AXON App:** the Director read these as AXON Web = network access (search, fetch pages, APIs, MCP servers) and AXON App = control of other apps and the screen (read screen text and images, tap, switch apps). Correct this if you meant something else. Advice: build the HANDS foundation first (tool bus, permission broker, journal), then AXON Web, then AXON App. Web is lower risk and is the main way knowledge comes in, so the truth gates must exist first. App control needs Android accessibility and screen-capture permissions and a store-policy check, so it comes last and one permission at a time, each visible in a Permissions screen.

## 4. The nine truth gates (Knowledge Gate), in order
G1 Provenance: who said it, where, when; no source means it stays REPORTED at best. G2 Source tier and credit: official or primary over peer-reviewed over reputable over community over anonymous, a recorded weight. G3 Independence: two sources that copy each other count once. G4 Date and expiry: stable, slow, fast-changing; fast facts expire. G5 Consistency: checked against the Charter and confirmed knowledge; a contradiction stops the claim and goes to the owner. G6 Test: if the claim can be run or computed, run it (PROVEN). G7 Scope: the claim is cut to what the sources actually say. G8 Adversary: look for the strongest counter-evidence and known failures. G9 Owner approval: required for anything high-stakes or behaviour-changing. Result: PROVEN, CONFIRMED, CHECKED, REPORTED, UNSURE or REJECTED, with the reasons stored. Only PROVEN and CONFIRMED are stated as facts. The knowledge about AI tools that "comes built in" goes through the same gates and is dated; AI tools change every few weeks, so each item has an expiry.

## 5. Where the Director would do it differently (opinions, as asked)
1. I would NOT build the brain stage by stage and bolt the loop on at the end. Build the loop SKELETON early (M1) with fake tools, because every later piece (memory, council, permissions, journal) plugs into it. Otherwise each stage invents its own plumbing.
2. I would build the PERMISSION BROKER and CHARTER first (M0), before any tool that touches the network, messages, files outside the app, or money. Safety added last is safety that is missing.
3. I would make corrections become TESTS. It is the single strongest "learning" mechanism available without a model, and it gives the owner exactly what was asked: tell it once, it never repeats that mistake.
4. I would not copy a famous council of models. Deterministic reviewers fit a weak phone and can be tested.
5. I would NOT allow AXON to clone itself, create accounts, or spend money on its own. What the owner described (several accounts, working in parallel, profit) can be met safely: PARALLEL WORKERS inside accounts the owner owns, each with a budget, a lane, and a journal; money and new accounts stay at ASK or NEVER with the owner as approver. Reason: an autonomous copy that spends money turns a single mistake into many, and the owner carries the loss. "Not to die" is honoured: AXON never deletes itself; failing a goal means it reports, learns and tries another way, within the fence.
6. The hunger example is right, with one change: AXON should do the immediate thing it is ALLOWED to do, and ASK before doing anything with a cost, a message to a person, or a risk. Doing and telling is the target; surprising the owner is not.
7. Imitating writing style: build a STYLE PROFILE from texts the person supplies (sentence length, punctuation habits, greetings, word choices), always as a DRAFT the owner approves. Own style freely; another person's style only with their consent, never to deceive the recipient about who wrote it. Predicting what a person wants is a safe, useful feature when it is shown as a suggestion with its reason.
8. "Make them feel loved" and leading a conversation toward a goal: build it as understanding the person and serving the goal HONESTLY. A hard rule in the Charter: no deception and no pressure tactics. Persuasion that is truthful and kind is a skill; manipulation is a liability and will be refused by the Guardrail reviewer.
9. Security testing like Claude does: yes, as a SECURITY LANE that only touches systems the owner has declared (scope file), reports findings with evidence, and suggests fixes. It audits AXON's own app (prompt injection, permission abuse, exported components, secrets in logs) and anything the owner owns. It does not produce weapons or attack other people's systems.
10. Reading WhatsApp and other messages and replying: technically possible only through notification access or accessibility; some apps forbid automation in their terms and can ban the account. Decide after a measurement and a terms check; start with DRAFTS only.
11. Voice: the phone's own recogniser turns sound into words; AXON cannot recognise speech without a downloaded model. AXON CAN clean the transcript before it is used: punctuation, apostrophes, capitals, fillers, false starts and self-corrections ("no, I meant ..."), names repaired from the owner's own dictionary, with the raw text kept and a one-line diff shown. That is the "filter before it is sent" the owner saw in other tools.
12. Writing that does not strain the eyes: the Writer has an audience model. For a person: short lines, one idea per paragraph, headings only when needed, no walls of text, plain words, the answer first. For an AI tool: complete, explicit, structured, with the success test and examples, and the known failure modes of THAT tool taken from a Tool Knowledge Pack (dated, tested). Before sending a prompt to another tool AXON asks: will this tool understand this, and what does it usually get wrong?
13. TURNING POINTS: knowledge that changes a plan's direction or quality. Implementation: during knowledge intake and planning, flag any claim that contradicts the current plan, reveals a hard constraint, or names a known failure; rank by impact times certainty; show the top few to the owner. Cheap, and it is the feature most likely to save the owner days.
14. THE GROWTH PATH the owner wants to repeat: MEASURE (corpora, mistake ledger, journal) > FIND the weakest area > GATHER knowledge through the gates or WRITE tests > FIX or ADD an ability > RUN every test and the golden transcripts > PROMOTE > LOG in a growth log the owner can read > repeat. Each turn leaves the system measurably better or it is rolled back.
15. Challenge Lab (the "walls" game): levels the owner designs, a sandbox with a budget, a score, a replay from the journal. Same loop, harder objectives. Built after the loop and the journal exist.
16. Sizes and phones: the owner is right that AXON is for every phone. Replace "the Infinix" in every budget with CAPABILITY TIERS measured by the Device Profile tool (memory, cores, storage, WebView version, a timed micro-test). Each feature declares the minimum tier it needs; heavy parts (Python, big knowledge packs, models) are optional downloads offered only where they fit; the base app works on the lowest tier with the same honesty. The owner's phone is a test device, and the plan also uses CPU-throttled preview runs as a low-end proxy.
17. Scripture: KJV Bible and the Book of Enoch as optional KNOWLEDGE PACKS with provenance and exact text (not paraphrase), searchable, never "interpreted" by AXON as its own claims. The Director believes the KJV text is public domain in the US and that R. H. Charles's 1917 translation of 1 Enoch is public domain; both must be verified (exact edition, source file, licence line) before shipping, and which Enoch translation the owner wants is an owner decision.

## 6. Decisions
Decided by the owner (2026-10-20): finish tools, then brain and mind, then AXON Code, then closing cleanup; AXON works for every phone; every capability reachable by chat; private and obedient; no amnesia (memory files, journal); fence with allowed, ask, never; Python wanted in AXON Code; Bible (KJV) and Book of Enoch to be added; video to audio and video frames tools wanted; calculator to be checked and improved.

## 7. Build order (mind system)
M0 Charter and permission broker (pure engine plus a Permissions screen). M1 Loop skeleton, step budget, success tests, journal (with fake tools). Then B3, B4 (stages and tool schemas), tools in chat. M2 Memory stores and standing files, corrections to tests. M3 Truth gates and tool certification (known-answer self-tests, known-bad registry). M4 Council and Verifier. M5 Objective model and the Writer (audience, Reading Comfort, Dictation Cleaner). M6 Lanes, scheduler, priorities, parallel workers. M7 Hands: tool bus, AXON Web, then AXON App. M8 Growth path, style profiles, Tool Knowledge Packs, scripture packs. M9 AXON Code harness, Security lane, Challenge Lab. Z Closing cleanup. Each job is written only after the one below it is accepted; the Director writes the corpus of right AND wrong cases before each.

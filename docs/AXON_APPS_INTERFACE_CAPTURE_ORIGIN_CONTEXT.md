# Why AXON Apps led to Interface Capture and Screen Intelligence

The starting idea was AXON Apps: a capability through which the user could see installed applications and navigate them, while AXON could also inspect and assist with those applications. That immediately raised a deeper requirement. A list of installed apps is not enough to understand or navigate an app. The system needs to understand the screen currently displayed: text, buttons, fields, icons, images, layout, dialogs, links, relationships and changes over time.

The existing AXON Interface Capture concept originally concerned AXON's own interfaces. During the discussion, we recognised that its capture foundation could be expanded into a shared capability. The original AXON-only purpose should remain identifiable, but a broader Screen Intelligence Engine should also observe user-authorised screens in supported external apps and AXON Web/Browser. The user must benefit directly; this must not be a brain-only facility.

Text extraction alone would be inadequate. The engine eventually needs OCR, image/icon/object recognition, visual context, knowledge comparison and optional external reference lookup. Video and rapidly changing screens introduced another problem: analysis may be slower than capture. If capture waits for OCR or visual understanding, important content can disappear before it is processed. Therefore observation, preservation and analysis were separated. Captured material should be timestamped, buffered, stored in recoverable segments and processed progressively. The system must report gaps rather than claim it captured everything.

The architecture also separates observation from actions. The user can navigate normally; a future action component may perform explicitly authorised interactions, but it must not be conflated with the reader. Android MediaProjection, accessibility, browser DOM and other platform mechanisms have different scopes and permissions, so platform adapters are required. AXON must adapt to each device's actual capabilities; the user's Android 11 / 4 GB phone is a test device, not a product hardware target.

Round 2 built the first capture/preservation foundation. Round 3 simulated event streams, permission loss, storage pressure, segment rotation, interruption, queue backlog, DOM visibility and native stop confirmation. The tests exposed defects in queue retention, per-session sequence reset, callback error reporting, stop confirmation and DOM visibility/URL handling. These were corrected. This origin note records the reasoning only; it does not claim that OCR, full visual understanding, accessibility-tree reading, automatic adaptive recording or app navigation are complete.

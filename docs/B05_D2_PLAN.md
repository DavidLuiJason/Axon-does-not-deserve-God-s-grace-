## Design
1. **Owner of the state:** the `createMind` closure holds ONE `DialogueState` (D0) and a new `resetDialogue()` on the Mind. `newChat()` and `selectRecent()` call it (Q5: fresh in every chat, never saved). This is the only app-screen file touched; it is one line in each function.
2. **Dialogue stage becomes real:** it runs after Resolution, before execution. With a live pending question it calls `readAnswer` (D1) and passes `newRequest = Resolution found a tool` (match, unavailable or ask). answers: the value goes to the lane as `slotAnswer`. cancels: reply "Okay, I dropped that." and clear. new-topic: clear and carry on normally. unclear: keep the question, carry on normally (the old handler answers; no re-ask in D2). none: nothing.
3. **Lane gets a third outcome, `ask`:** when the binder says ask and the ONLY missing slot is one required text slot, the lane returns the question instead of yielding. The execution stage stores it with `setPending` (kind text-slot, slot, tool) and records the turn (tool, bound args as strings) with `recordTurn`. Any other kind of missing slot still yields as today.
4. **The next turn:** the lane gets `slotAnswer { slot, value }` and the tool and args from the turn record, fills the slot and runs. The part 1c QUOTE GUARD must accept text that came from `slotAnswer` (the owner answered a direct question; quote marks are not needed). The guard stays for text found in the message itself (LIVE8-2e).
5. **One owner of the pending question:** while the old `asking.ts` provider holds a conversation (`holdsConversation()` true) the lane already yields and the new state does nothing. D5 retires the old one.
6. **Wording (Q9, default):** "What text should I use? Send it as your next message, or say cancel." (the tool's name is added when the tool is not obvious). The owner can change the sentence; it is one string.
7. **Switch:** `dialogue` in the lane config, OFF by default, per tool (Case Converter first, then Text Counter), like the runner switches. Nothing changes for the owner until the phone check passes.
## Parts
- **D2a (shadow, no reply changes):** the Mind holds the state and records every turn; the dialogue stage runs `readAnswer` and writes a real trace entry; `resetDialogue()` exists and is called by `newChat()` and `selectRecent()`. Proof: transcripts show state and trace only; replies byte-identical on the lane tests and the golden.
- **D2b (live, behind the switch):** lane `ask`, `slotAnswer`, guard exception, cancel reply. Proof: about 40 multi-turn transcripts through the REAL brain (`tests/fixtures/dialogueLaneCorpus.json`): ask then answer then run; ask then cancel; ask then a new request; ask then an unclear reply; expiry after 3 turns; nothing survives `resetDialogue()`; the old conversation provider wins; switch off gives today's reply; plus 10 deliberate breakages. Also 3 phone messages for the owner.
## What could break
Bound args that are not strings (numbers, quantities) lose their type when stored as strings: D2b starts with tools whose args are strings (Case Converter, Text Counter) and re-binds the ORIGINAL message with the slot filled for any other tool (HYPOTHESIS: the re-bind is the safer route; measure first). A turn that both answers the question and is a request (`convert "hi" to uppercase`) is read as new-topic by design. The shared Brain means two screens would share one state: today there is one chat screen.

## Owner rule added 2026-11-01: PARKING (supersedes "new-topic: clear" in design point 2)
When the owner changes topic while a question is open, AXON follows the NEW topic and keeps the open question PARKED: it stays pending until it expires after 3 turns, and AXON may mention it afterwards (the mention is D2b). Only an answer or a cancel clears it. Built as a shadow in D2a (`dialogueDriver.ts`, `stepDialogue`); proven by `tests/dialogueShadow.test.ts`.

(c) a resource not in the capacity vector is refused with `unknown-resource` (so "we have no number for battery" has no representation: it is an error, not UNKNOWN). ## 2. Decisions (B1 to B9)
- **B1 PLACEMENT: KEEP THE ENGINE, ADD A THIN PURE VIEW ABOVE IT (FL14).** `budgetBroker.ts` stays the one accounting engine; no second engine. New pure file `src/budget/budgetView.ts` takes a request (a resource vector in ONE domain, a depth the caller wants) plus that domain's state and returns the BUDGET output of 7E and DECISION DIMENSIONS: `AVAILABLE`, `CONSTRAINED`, `BLOCKED` or `UNKNOWN`, with reason codes. It never sets route, depth or permission (five separate outputs); it only reports. No Date, random or IO (the caller passes time).
- **B2 FOUR DOMAINS, FOUR STATES, NEVER ADDED TOGETHER.** DEVICE (RAM, CPU time, storage, battery, thermal, network, foreground or background), TASK (steps, files, output size, tests, tool calls), ACCOUNT (provider, model, account, plan, context load, attachments, turns, visible limit events), BUILDER (builder memory, archive expansion, repo files, test time, Director review capacity). Each domain has its own `BudgetState` from `newBudget`; resource names live in ONE closed-set file per domain (FL13: structure, owner approves; a name not in the file is refused). Reports are per domain; there is no single "budget score".
- **B3 THE VIEW'S FOUR OUTCOMES, EXACTLY (interpretable, no score).** BLOCKED: some requested resource would be over capacity (the engine's `over-budget`) or is already overrun (`remaining` below zero). CONSTRAINED: it fits, but a resource would drop under a margin (default 20 percent of capacity, a per-domain table value, HYPOTHESIS) or only the verification reserve is left. UNKNOWN: a requested resource has no capacity figure for this domain or tier, or its figure is ESTIMATE from fewer than the sample minimum (B4) while the request is large; UNKNOWN is never shown as AVAILABLE and never blocks by itself (unsure goes UP: the caller then plans a small probe or asks). AVAILABLE: every requested resource has a figure and fits with the margin intact. The order of checks is BLOCKED, then UNKNOWN, then CONSTRAINED, then AVAILABLE; the first match wins and ALL reason codes found are kept.
- **B4 ESTIMATE BECOMES OBSERVED ONLY WITH SAMPLES (fixes measured gap (a)).** `basis` is `OBSERVED` only after at least N settled samples for that resource and key (N = 5, HYPOTHESIS, a table value the owner may change); below it the view reports `ESTIMATE` with the sample count, and the figure is an estimate even if one run was measured. Each sample keeps its date (passed in). Job BUD2 adds a `samples` count per resource to the engine state (a compatible addition; the 36 existing checks must still pass unchanged).
- **B5 OVERRUN IS AN EVENT, NOT A HOLE.** The engine keeps accepting an actual above capacity (the work already happened: refusing the record would hide it). The view turns a negative `remaining` into BLOCKED with reason `overrun`, and the caller writes one MISTAKE LEDGER or interaction-journal line (7Q, 7T) so the estimate behind it is re-examined (FL15 4). An overrun never lowers a capacity figure by itself.
- **B6 UNKNOWN RESOURCE IS DATA (fixes measured gap (c)).** The view maps the engine's `unknown-resource` to UNKNOWN with reason `no-figure` and the resource name; it never drops the resource from the request and never invents a number (honesty: never state a number you did not measure).
- **B7 SAFE RANGES COME FROM SMALL PROBES, NEVER FROM DRIVING A LIMIT.** A PROBE RECORD is `{domain, provider, model, account, taskClass, workloadShape, samples, lastDate, low, high}` (account and provider are labels for the owner's own accounts; never passwords, keys or tokens). A probe is at most a fixed fraction of the last known safe range (start 10 percent, HYPOTHESIS), runs only for ESTIMATE or missing figures, and is never run against a metered, paid or capped resource without the owner's yes (that is `costly`, B8). ACCOUNT limit events are OWNER-REPORTED (the owner pastes the message and time) and enter as one probe sample marked REPORTED, never VERIFIED (7F 7). Records live in USER DATA (N3), a later storage card; the engine reads and writes them as plain data (7D: nothing hidden, the owner can see and clear them).
- **B8 WHAT BUDGET FEEDS TO J6 (closes D6).** `costly` for J6 means COST TO THE OWNER: the request would use a resource flagged `ownerCost` in the closed set (a capped, metered or paid outside-AI call, data over his cap; the P9 data-use tracker supplies the data figure) by more than a threshold the Charter holds (CHR1: fence `maxSpendPerAction` style). Phone time and memory are NEVER costly. Until BUD2 and BUD3 exist the caller still passes false; the first wiring is the FEED3 card, which reads `costly` from the view. A BUDGET outcome of BLOCKED or UNKNOWN on an ownerCost resource makes the caller ASK (APPROVAL), never act.
- **B9 RULES THE VIEW ENFORCES, THE CALLER OBEYS (7T, P19).** (1) Least depth that is sufficient. (2) The verification reserve is taken first (the engine already holds it back from `work` reservations). (3) When short: save the work (write-ahead journal), say so in plain words, offer a smaller scope. (4) Never claim a test ran that did not. (5) Never silently lower a depth the owner asked for: if the budget cannot cover it, AXON says so and asks; a depth AXON chose itself may drop one step and says so. (6) Queue states QUEUED, RUNNING, PAUSED, WAITING_FOR_OWNER, BLOCKED, COMPLETED, FAILED are a pure transition table (an illegal move is refused); it sits in `src/budget/queueState.ts`, separate from the scheduler (`when`) and the journal (`what was done`).

## 3. Hand-worked EXAMPLES (illustration only, never stored as sentences: FL13 rule 13)
Capacity TASK steps 10, verification reserve 1, work ceiling 9. Request 8 steps: remaining 2 of 10 (exactly the 20 percent margin, not under it): AVAILABLE. Request 9 steps: fits the ceiling, remaining 1 of 10 is under the margin: CONSTRAINED, reason `margin`. Request 10 steps: over the work ceiling: BLOCKED, reason `over-budget`. Request steps 3 and `battery` 1 where DEVICE has no battery figure for this tier: UNKNOWN, reason `no-figure: battery`; the caller plans a probe or says it cannot judge. A tool with `cost.time slow` on the weak tier and no measured figure: UNKNOWN (not CONSTRAINED), because the schema cost is an estimate (it only raises the request size for the check). One run measured: still `ESTIMATE (1 of 5 samples)`. Five runs measured: `OBSERVED`. A run uses 51 of 10 steps: the engine records it, the view says BLOCKED `overrun`, a ledger line is written.

## 4. Honest verdicts (rule 12; probabilities are HYPOTHESES)
- View, domains, four outcomes, queue transition table, overrun handling: WORKS (pure, hand-worked, mutant-testable). About 90 percent.
- Per-tier DEVICE numbers: CANNOT JUDGE until measured on each tier (BM1, rule 8); the owner's phone is one test device. Until then DEVICE answers UNKNOWN, which is the honest state, and AXON asks or plans a small probe.
- ACCOUNT domain: WORKS ONLY IF the owner reports limit events (the Director and AXON cannot read an account meter); about 60 percent that the reports are frequent enough to learn a range.
- Safe ranges learned from probes: WORKS ONLY IF enough samples exist per key (provider x model x account x task class x workload shape); many keys will stay UNKNOWN for a long time.
- Plan B batch size packed from the BUILDER vector: WORKS ONLY IF the capacity log (`DIRECTOR_LIMITS.md`, `AI_CAPACITY.md`) is turned into numbers; it has estimates only today.

**Rival/gap (rule 9):** assistants ask by feel. Here every question traces to a declared fact: a schema field, a Resolution result, a bind default, or the Charter.

## 1. Where it sits (FL1)
Resolution (stage 5, `resolve.ts`) returns a `Resolution`; the schema (`actionSchemas.ts`, B04A) declares effects, undo, cost; bind defaults (`bindDefaults.ts`, `SLOT_DEFAULTS[tool][slot]`) say which slots have an approved default. A NEW pure engine, the FEED (`src/decision/actOrAskFeed.ts`), turns those into `ActOrAskInput`. J6 decides. Then Dialogue (stage 6) words the question; THEN J2 records the decision. The feed and J6 never see the message text (FL13). Nothing calls the feed yet.

## 2. Which results reach J6
Only `match`, `ask` and `none`. `not-a-request` stays conversation. `negated` is a refusal ("do not"): never acted on. `unavailable` goes DEEP, not ASK (ROUTER DEFAULT R8). Resolution's `confidence` is NOT read (7E: no confidence figure before calibration).

## 3. The eight facts (decided)
| J6 input | Comes from | Rule |
|---|---|---|
| readings | Resolution kind, plus repair readings (7K) | `match` with no second reading: ONE-CLEAR. `ask` (2 to 4 tools), or a `match` plus a repaired reading naming a DIFFERENT tool: TWO-CLOSE. `none`: NO-READING. A match found ONLY by value evidence (`evidence: 'value'`): TWO-CLOSE (the other reading is "not a request"; HYPOTHESIS, test on the golden transcript, pass count must not drop). |
| readingChangesResult | the readings' tool ids | true exactly when readings is TWO-CLOSE (repairs that all complete the SAME tool collapse to ONE-CLEAR, so a TWO-CLOSE pair always names different tools). |
| undo | `schema.undo` | `not-needed` -> READ-ONLY; `by-tool` or `by-removal` -> UNDOABLE; `irreversible` -> NOT-UNDOABLE. With two readings: the WORST of them (NOT-UNDOABLE > UNDOABLE > READ-ONLY). Unsure goes UP: `not-needed` on a tool with any non-PURE effect is mapped to NOT-UNDOABLE, never passed on (J6 would reject READ-ONLY with an effect). |
| outward | `schema.effects` | `sends` -> SEND, `deletes` -> DELETE, `spends` -> MONEY, none -> NONE. J6 holds ONE value: if several, the worst, MONEY > DELETE > SEND (MEASURED: no schema today has two). With two readings: the worst of them. |
| costly | the caller (BUDGET broker, later) | FALSE until that broker exists (section 5 D6): `costly` is cost to the OWNER (a capped, metered or paid resource), never phone time or memory. MEASURED: 24 of 63 schemas are `slow` and 13 `high` memory (all estimates); asking approval on those would interrupt most runs. Money is already `outward: MONEY`. |
| permission | Charter view (7A), else the schema | per tool: `NEVER` if its id is in the Charter `never` list; `ASK` if in the `ask` list, or it has precondition `owner-approval` (4 schemas), or an approval effect; else ALLOW. Over all readings the STRICTEST wins (a forbidden reading blocks, a safe outcome); nothing ever lifts an ask. The Charter store is not built: the feed takes the read-only view `{never, ask}` (tool ids). |
| missing | `match.missingSlots`, bind defaults, context | per missing required slot: CONTEXT-ANSWERS if the conversation supplies it, SAFE-STEP-ANSWERS if a read-only step can fetch it, else OWNER-ONLY. Several slots: the worst, OWNER-ONLY > SAFE-STEP-ANSWERS > CONTEXT-ANSWERS > NONE. `ask` and `none` results have no slots: NONE. Context and safe steps do not exist yet: the feed takes `contextFills` and `safeStepFills` (slot names) as typed arguments. |
| inputChangesResult | `SLOT_DEFAULTS[tool][slot]` | false when EVERY OWNER-ONLY slot has an approved default (AXON acts and says the default aloud: bind-default rule); true when any has none (no default means AXON cannot proceed, so it asks). |

## 4. Recording in J2 (MEASURED, no J2 change needed)
J2 refuses `permission ASK` unless the question is APPROVAL, and refuses an APPROVAL question unless `permission` is ASK. I ran all 2,592 valid J6 inputs through J2 two ways. **Mapping the INPUT permission straight across: J2 rejects 808** (350 ALLOW with an approval ask, 400 ASK with a clarification, 58 ASK with a missing-input ask). **Mapping the EFFECTIVE permission (BLOCK -> NEVER, ASK APPROVAL -> ASK, everything else -> ALLOW): J2 rejects 0.** DECIDED: J2's `permission` means "what the broker does with this decision now". When J6 asks a clarification while the Charter says ASK, the record says ALLOW with the clarification; after the owner answers, the whole decision runs again and the approval question comes THEN. One question at a time. Question text comes from Dialogue after J6; J2 needs 1 to 200 characters and one `?` at most, so the record is made after the wording, never by J6. `stepsLeft` and `route` come from the Router and budget (7E, not built).

## 5. DECIDED under the owner's permission (2026-11-05, "think how you would do it, the most professional way; do it yourself, this once"; recorded on the board; the owner may overrule; each item names why)
- **D1 CALLER.** The Router (7E) is the ONLY caller, once per clause, after Resolution, SHADOW ONLY (ROUTER DEFAULTS: no switch). Order per clause: Resolution (with repair readings) -> feed -> J6 -> ASK: Dialogue words ONE question, then J2 records; ACT: Planning receives the step. J6 never sets route or depth (separate outputs, 7E). A later Director check proves consistency: J6 never returns ACT for a tool the Router sends DEEP by R3 (irreversible or approval effect). Several clauses in one message: every clause runs; a BLOCK is reported; only ONE question is asked per turn, in the order CLARIFICATION, MISSING-INPUT, APPROVAL (the answer that settles most of what follows comes first); the others wait in the trace and are asked after the answer (MR1: a split is kept only if every part resolves). Go-live needs the owner's yes and a golden transcript pass count that does not drop. Why: one caller keeps one decision path (FL12).
- **D2 CONTEXT AND SAFE STEPS.** `contextFills` = slot names filled from CONTEXT (7A, task input) ONLY: the owner's previous message in this chat, an object he attached or selected now, his earlier answer in this task. NEVER from long-term memory notes unless he referred to them (7D). `safeStepFills` = slots a SAFE STEP can fetch: a registered tool step whose effects are all pure (shows-result, reads-file, uses-camera, uses-microphone, uses-network), cost instant or quick, undo not-needed, run through the tool bus; v1 supports reading a file he attached. Until the Context lookup (CTX1) exists both lists are EMPTY: AXON asks more and never guesses (unsure goes UP).
- **D3 REPAIR READINGS.** They arrive as `extraReadingTools` (tool ids of the other readings, from Resolution's second-reading rule and repair), at most 4, valid only beside `match` or `ask` (a repaired reading that wins is folded into Resolution's result, never passed twice). When repair passes its limits (3 repairs per message, 4 readings per piece) the caller sends kind `none` and AXON says plainly it could not repair the message (FL15 loud). A repair never sets any other fact.
- **D4 QUESTION WORDING.** Dialogue words the question AFTER J6, from askKind and the facts, never as a stored sentence per scenario (7D FLEXIBLE SPEECH). Tested PROPERTIES, not sentences: exactly ONE question; 1 to 200 characters and at most one `?` (J2's limits); CLARIFICATION names every reading by its tool name; MISSING-INPUT names the missing slot; APPROVAL says the effect (sends, deletes, spends, cannot be undone) and exactly what would be done; no developer terms (owner design fix 2); never asks what context answers. WORKS inside these properties with closed structure pieces the owner approves (FL13); free personal phrasing WORKS ONLY IF the optional model tier exists. Build: DLG1, design first.
- **D5 CHARTER VIEW.** The feed receives a read-only view `{never, ask}` of tool ids. The store lives in user data, is written ONLY by an owner-confirmed Settings action, loads before the first screen, and AXON and every outside AI have no write path (a test proves it, N3 style). Shipped default: no `never`; `ask` for every tool with an approval effect (sends, spends, deletes), which is 7A (start ASK) and W12 (money needs ASK or a hard cap). The strictest wins: a Charter entry can tighten, never loosen. Build: CHR1, design first (7A).
- **D6 COSTLY (DIRECTOR READING of 7K).** J6's `costly` means COST TO THE OWNER: a capped, metered or paid resource (data over his cap, a paid outside-AI call; P9 tracker, 7T BUDGET broker). Phone time and memory (schema `cost`) belong to BUDGET (7T), a separate output (7E: five separate outputs, never one overloaded label), never to J6. Until the BUDGET broker exists the caller passes false. Measuring phone costs is a BUDGET job per device tier (rule 8), not a J6 job.
- **D7 VALUE-ONLY EVIDENCE.** Shipped as designed (TWO-CLOSE) in shadow. Keep or drop is decided by numbers (FL7): keep if the golden transcript pass count does not drop AND a held-out set (7L 7) shows no value-only clause wrongly run; otherwise drop to ONE-CLEAR plus the Router's existing confirm step (C1). One variable changes, nothing else.

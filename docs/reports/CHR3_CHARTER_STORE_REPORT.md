# CHR3 Charter store and single writer (Director job, 2026-11-06)
Placement: layer 5, roadmap 7A and N3; design `docs/CHR1_CHARTER_STORE_DESIGN.md` C6 and C7; builder: the Director (small risky piece); proof: `tests/charterStore.test.ts`. DESIGN-FIRST EXIT used (isolated, no caller; nothing imports it).
## What it is
`src/mind/charter/charterStore.ts` (about 80 lines). A storage interface (getItem, setItem, removeItem) the caller passes in, so no localStorage in the engine; `browserCharterStorage()` is the one place that touches `window.localStorage`, behind try/catch, null when absent. `readCharter` (a read error is "unreadable", never "absent"), `readCharterHistory`, `previewCharterChange` (what the owner approves: the change hash for a widening and the hash of the resulting Charter for the signature; writes nothing), and `writeCharter`, the ONE writer: proposeChange as owner, applyChange (widening needs the owner's approval), signCharter (always needs a second owner approval for the resulting hash), serialize, history FIRST (the replaced text, marked `[replaced DATE]`, at most 20, newest last), then the Charter, then a read-back check; a failed check restores the old text (or removes a first write). Keys: `axon.charter.v1`, `axon.charter.history`.
## Proof (MEASURED, Director sandbox)
`tsx tests/charterStore.test.ts`: CHARTER_STORE OK, 43 checks: reads, narrowing write, second write keeps the exact replaced text, 7 widening failures each leaving storage byte-identical, untrusted store and corrupt history refuse to write, 5 storage failure paths, history cap with 22 writes, the whole `src/` tree byte-identical after Charter writes (N3), and the single-writer ratchet (no file in `src/` outside `charterStore.ts` mentions the writer, the keys or the module; the scanner is itself tested on a writer import, a key use and a re-export). 13 Director mutants, all killed (history order, corrupt history ignored, untrusted overwrite, origin, cap, read-back skipped, rollback, read error as absent, first replaced text, used tokens, preview writing, unsigned write, history note). The view and the store agree: a written rule shows in `charterToFeedView`.
## Findings (for the SET-CHR design; none blocks CHR3)
F1 an untrusted or corrupt stored Charter, or a corrupt history, REFUSES every write and has no reset path: SET-CHR needs an explicit owner reset (with the old text kept). F2 the used-token set is supplied by the caller and not stored: an approval could be replayed after a restart until it expires; SET-CHR must persist tokens (they also sit in each signature). F3 history is capped at 20 (CHR1 C6): the oldest entry is dropped. F4 history is written first, so a failed Charter write leaves one duplicate history entry (harmless, never a loss). F5 a patch replaces a WHOLE lane: the Settings screen must send the full lane. F6 localStorage survival on weak phones is UNMEASURED (DEVICE, rule 8). F7 the real `sha256` the app will pass is not chosen yet (the tests use a small test hash).
